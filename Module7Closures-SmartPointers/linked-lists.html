Linked lists, one key at a time

A linked list is a row of lockers. Each locker holds a number and the only key to the next locker. This page is about holding those keys in Rust: looking at a list, taking it apart, building a new one, and knowing what every move costs the machine.

What we're working with

Every list on this page is made from one small struct. It is already written for you. You never type it yourself, you only use it:

#[derive(PartialEq, Eq, Clone, Debug)]
pub struct ListNode {
    pub val: i32,
    pub next: Option<Box<ListNode>>,
}

impl ListNode {
    #[inline]
    fn new(val: i32) -> Self {
        ListNode { next: None, val }
    }
}

Two fields. val is a number. next is where the rest of the list hangs. That type on next, Option<Box<ListNode>>, is what this whole page is about, so if it reads like noise right now, good, that's the right starting point. By the end it should read like a plain sentence.

The #[derive(...)] line and the impl block get explained later (sections 12 and 11). For now you only need one thing from them: ListNode::new(5) makes a single node holding 5 with nothing after it.

Now the picture that will carry us through. Imagine a row of lockers in a train station. Each locker holds two things, a number and the key to the next locker. The last locker holds a number and an empty key hook. You get handed exactly one key: the key to the first locker.

That one key really is the whole list. Open locker 1, find key 2, open locker 2, find key 3, keep going until a hook is empty.

The row has one strict rule, and Rust enforces it every single time: each locker has exactly one key, and keys can't be copied. Hold on to that. Nearly every surprise later on comes from this rule. So does nearly every trick.

Work with lists comes in three kinds.

  • Reading. Walk the row and pull out an answer: a number, a yes or no, a Vec of values. The lockers stay as they were.
  • Rearranging. Take the lockers you were handed and hang them in a new order, or throw some away. No new lockers.
  • Building. Rent new lockers and hand back the key to the first one.

Real tasks mix these. The sections go in order, each one adding a little to what you can do, so section 6 assumes you've read 1 to 5.

1

Keys and hooks

Start with Box. When you write Box::new(something), two things happen. The program asks the allocator (the part of the runtime that hands out heap memory) for a piece of memory big enough for something, and moves something into it. What you get back is small: the address of that piece of memory.

A Box is that address plus a promise. The promise is ownership: the box is the one and only owner of what it points at, and when the box goes away the memory goes back to the allocator automatically. You never free anything by hand.

In locker language, Box::new rents a locker, puts your thing inside, and gives you the key.

Next, the last locker's hook, which has to say "nothing here." Rust has no null pointer you can trip over by accident. It has Option, which is either Some(x), meaning there is an x, or None, meaning there isn't. So:

Option<Box<ListNode>>  reads as  maybe a key to a locker that holds a ListNode.

That's a hook. It has a key on it, or it's empty. Every next field is a hook, and so is the variable that holds the start of a list.

How much does the "maybe" cost? Run this and see:

println!("{}", std::mem::size_of::<Box<ListNode>>()); // 8
println!("{}", std::mem::size_of::<Option<Box<ListNode>>>()); // 8
println!("{}", std::mem::size_of::<ListNode>()); // 16

factOn a 64-bit machine that prints 8, 8 and 16. A Box is 8 bytes because an address is 8 bytes. The Option wrapped around it is also 8 bytes, because Rust guarantees that None is stored as address zero, which no real box can ever have. An empty hook weighs exactly as much as a hook with a key on it. The node is 16 bytes: 4 for the number, 8 for next, and 4 bytes of padding that round the node up to a multiple of 8, because it contains an 8-byte address.

Building one by hand

Here's a three-node list written out in full:

let list = Some(Box::new(ListNode {
    val: 1,
    next: Some(Box::new(ListNode {
        val: 2,
        next: Some(Box::new(ListNode::new(3))),
    })),
}));

Read it from the inside out, the same way you read the type. The innermost Box::new(ListNode::new(3)) makes the last locker. That box goes into the next of node 2, wrapped in Some to say "a key is on this hook." Node 2 gets boxed and goes into the next of node 1. ListNode { val: 1, next: ... } is struct literal syntax: name every field, give each a value.

Nobody writes long lists like that. The same list, one step at a time:

let mut a = Box::new(ListNode::new(1));
let mut b = Box::new(ListNode::new(2));
let c = Box::new(ListNode::new(3));
b.next = Some(c); // c now hangs inside b
a.next = Some(b); // b, carrying c, now hangs inside a
let list = Some(a);

Look at the order. After b.next = Some(c); the variable c is done. Its key moved into b's locker, and c can't be used again. Same for b after the following line. That's a move: ownership changed hands, and nothing got copied except an 8-byte address.

The other order doesn't compile

a.next = Some(b); // b moves into a
b.next = Some(c); // b is not yours anymore

Once b's key is inside a's locker, writing into b means reaching into a locker you no longer hold the key to. Rust refuses.

And the smallest list of all:

let empty: Option<Box<ListNode>> = None;

An empty list is an empty hook. Every function in this page has to work when it's handed one of these, which is easy to forget and a common reason code crashes on the simplest input.

2

Looking

Most of the time you want an answer out of a list and the list itself should stay exactly as it was. You don't want to open any lockers. You want to walk down the row with a flashlight and read the numbers through the little windows.

Rust's word for looking is a shared reference, written &. If head is a list, &head lets you see it without owning it. Any number of lookers can exist at once. None of them can change a thing. Underneath, a reference is also just an address, 8 bytes.

fn length(head: &Option<Box<ListNode>>) -> usize {
    let mut count = 0;
    let mut cur = head;
    while let Some(node) = cur {
        count += 1;
        cur = &node.next;
    }
    count
}

Take it a line at a time.

  • cur starts as a look at the first hook.
  • while let Some(node) = cur means: as long as the hook cur is looking at has a key on it, call the locker node and run the body. Once the hook is empty, the pattern Some(node) doesn't match and the loop ends.
  • Inside, node is a look at a box. You write node.val and Rust follows the box to the locker for you.
  • cur = &node.next; moves your flashlight one hook down.

That loop shape is the single most common thing on this page. Type it from memory a few times, until your fingers know it without you.

When the list arrives by value

Plenty of functions receive the list itself, not a reference. You own it. You can still just look:

fn digits_value(head: Option<Box<ListNode>>) -> i64 {
    let mut value = 0;
    let mut cur = &head;
    while let Some(node) = cur {
        value = value * 10 + node.val as i64;
        cur = &node.next;
    }
    value
}

let mut cur = &head; and the rest is identical. When the function ends, head goes out of scope and the whole list is freed, which is fine, nobody needed it. (node.val as i64 converts the 32-bit number to 64 bits so a long run of digits doesn't overflow.)

Remembering the one before

Lots of questions compare a node with its neighbour. But a locker has no idea who comes before it. Nothing in the row points backwards. So you carry the previous value yourself, in an ordinary variable:

fn count_rises(head: &Option<Box<ListNode>>) -> i32 {
    let mut rises = 0;
    let mut prev = 0;
    let mut first = true;
    let mut cur = head;
    while let Some(node) = cur {
        if !first && node.val > prev {
            rises += 1;
        }
        prev = node.val;
        first = false;
        cur = &node.next;
    }
    rises
}

The first flag stops the very first node from being compared against a made-up previous value. You could look ahead at node.next instead of carrying the past around, and that works too, but every look ahead means checking whether the next hook is empty. Carrying the previous value is usually less typing.

Copying the numbers out

Some questions are the wrong shape for a list. "What's the third value from the end?" A list only walks forwards, and it doesn't know its own length. A Vec lets you jump to any position. So copy the numbers into one:

fn to_vec(head: &Option<Box<ListNode>>) -> Vec<i32> {
    let mut values = Vec::new();
    let mut cur = head;
    while let Some(node) = cur {
        values.push(node.val);
        cur = &node.next;
    }
    values
}
fn kth_from_end(head: &Option<Box<ListNode>>, k: usize) -> i32 {
    let values = to_vec(head);
    values[values.len() - k]
}

judgmentThis costs one walk and one i32 per node of extra memory. What you buy is random access: values[i] for any i, both ends at once, sorting, the lot. When memory isn't the constraint it's often the clearest code you can write. When a task insists on working in place with constant extra memory, it's off the table, and that's what most of the rest of this page is for. Section 9 shows there's a speed side to this as well.

Looking means looking

let rest = node.next; // node is only on loan

Inside a looking walk, node is on loan. You can look at node.next (that's &node.next), but carrying it off would mean taking a key out of a locker you're only allowed to peer into.

3

Clearing as you go

Now open the lockers. If a function owns the list and won't need it afterwards, it can walk by moving instead of looking:

fn digits_value(head: Option<Box<ListNode>>) -> i64 {
    let mut value = 0;
    let mut cur = head;
    while let Some(node) = cur {
        value = value * 10 + node.val as i64;
        cur = node.next;
    }
    value
}

Put it beside the version from the previous section. The only difference is a missing &. One character, and the meaning changes completely:

  • cur is the hook itself now, not a look at a hook.
  • node is the box itself. You own it.
  • cur = node.next takes the key out of node's locker and puts it in cur.

At the end of each pass, node goes out of scope, and what's left of it (the number, plus an empty spot where the key was) gets freed right there. The list disappears behind you as you walk. Open locker 1, pocket key 2, hand locker 1 back at the desk, walk on.

factPulling a field out of the thing a Box points at, like node.next here, is something Box allows and most other pointer types in Rust do not. This page leans on that a lot. Each move shifts 8 bytes; nothing gets copied.

There's a price, of course. When you're done, the list is gone.

Using it afterwards doesn't compile

let value = digits_value(head); // head handed over by value
println!("{:?}", head); // nothing left to print

The keys were handed over. There's nothing left in head to print.

So why consume at all, when looking works? Because rearranging needs nodes in hand. You can only re-hang a locker you hold the key to. Sections 4 through 8 are all built on this walk.

Two rows at once

Walking two lists side by side, until both run out, uses two new small pieces:

fn total_of_both(l1: Option<Box<ListNode>>, l2: Option<Box<ListNode>>) -> i32 {
    let mut total = 0;
    let mut a = l1;
    let mut b = l2;
    while a.is_some() || b.is_some() {
        if let Some(node) = a {
            total += node.val;
            a = node.next;
        }
        if let Some(node) = b {
            total += node.val;
            b = node.next;
        }
    }
    total
}

a.is_some() asks whether there's a key on hook a without touching anything. if let is while let that runs at most once.

The interesting line is if let Some(node) = a. If a has a key, the pattern moves it into node. For a moment a holds nothing usable at all, not even None, and two lines later it gets a fresh value, node.next. If a was already empty, the pattern doesn't match and nothing moves at all. Rust follows both possibilities and is happy that a is usable again by the next check.

That loop is a skeleton. Anything that combines two lists position by position, digit by digit, hangs off it.

4

Dealing the deck

The cheapest change you can make to a list is putting a new locker at the front. Make a node whose next is the old list, box it, and that box is the new head:

fn push_front(head: Option<Box<ListNode>>, val: i32) -> Option<Box<ListNode>> {
    Some(Box::new(ListNode { val, next: head }))
}

No walking at all, however long the list is. (ListNode { val, next: head } uses a shorthand: when a variable has the same name as the field, val means val: val.)

Because each new value lands in front, building a list from a Vec this way means going through the Vec backwards:

fn from_values(values: &Vec<i32>) -> Option<Box<ListNode>> {
    let mut head = None;
    let mut i = values.len();
    while i > 0 {
        i -= 1;
        head = Some(Box::new(ListNode {
            val: values[i],
            next: head,
        }));
    }
    head
}

Reversing

Take a deck of cards face up and deal them one at a time onto a new pile. The new pile is the old deck backwards. You didn't print a single new card. You only moved them.

Reversing a list is exactly that. Step through it:

fn reverse(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut prev = None;
    let mut cur = head;
    while let Some(mut node) = cur {
        cur = node.next;
        node.next = prev;
        prev = Some(node);
    }
    prev
}

Three lines in the loop, always in this order:

  1. cur = node.next; pocket the rest of the deck,
  2. node.next = prev; point this card at the pile,
  3. prev = Some(node); and now it's the top of the pile.

Some(mut node) needs the mut because line 2 changes the node.

Between lines 1 and 2, node has a hole in it. Its next was moved out and nothing is there yet. Rust tracks holes like that, and allows them as long as the hole is filled before the node is used as a whole again. Line 2 fills it. Section 6 shows what happens when it isn't filled.

factReversing 1000 nodes this way, measured with an allocation counter: zero allocations, zero frees. Every locker stays exactly where it is in memory. Only keys move, 8 bytes at a time.

Reverse, work, and let prepending undo it

Numbers stored with the biggest digit first are awkward. Carries travel right to left, and the list only goes left to right. Reverse first, and the smallest digit is at the front. Then build the answer by prepending, and the order comes back on its own:

fn plus_one(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut cur = reverse(head); // smallest digit first now
    let mut result = None;
    let mut carry = 1;
    while let Some(mut node) = cur {
        cur = node.next;
        let d = node.val + carry;
        node.val = d % 10;
        carry = d / 10;
        node.next = result; // prepending puts the order back
        result = Some(node);
    }
    if carry > 0 {
        result = Some(Box::new(ListNode {
            val: carry,
            next: result,
        }));
    }
    result
}

This is reversal with two extra lines in the middle. It reuses every node; the only allocation happens when the number grows a digit (99 becomes 100).

judgment"Reverse, do the work, prepend" handles a whole family of tasks: anything where a node's fate depends on what's to its right. Walk from the right end, carry what you need (a carry digit, a running maximum, a count) and prepend whatever survives. You get the answer in original order without a second reversal.

5

Building in order

Prepending builds backwards. Often you want the output in order. One plan: prepend everything, then reverse at the end. That's honestly fine, one more pass and no extra memory. The other plan is to keep a thumb on the last locker, so the next one can always go on its hook.

That thumb needs a new kind of reference. & only lets you look. &mut lets you change what it points at. The rule for &mut is strict: while a &mut loan is alive, it's the only way in. No other lookers, no other changers. One person in the locker room, with the door shut.

There's one annoyance. The first locker has nothing before it to hang on, so the first append would need its own special code. The usual way out is a small cheat: a cardboard locker zero. Make a throwaway node, hang everything after it, and at the end return what hangs after the cardboard.

fn squares(n: i32) -> Option<Box<ListNode>> {
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut i = 1;
    while i <= n {
        tail.next = Some(Box::new(ListNode::new(i * i)));
        tail = tail.next.as_mut().unwrap();
        i += 1;
    }
    dummy.next
}

The new piece is tail.next.as_mut().unwrap(). Read it right to left from the hook:

  • tail.next is a hook.
  • .as_mut() turns "the hook" into "maybe a changeable look at the locker on that hook", an Option<&mut Box<ListNode>>.
  • .unwrap() says: there's definitely something there, hand it over. If the hook turns out to be empty, the program stops on the spot with a panic.

Here it can't be empty. You hung a locker on that exact hook one line earlier.

Where the cardboard lives

The dummy above is a plain ListNode sitting in the function's stack frame. You'll often see it on the heap instead:

let mut dummy = Box::new(ListNode::new(0)); // dummy on the heap
let mut tail = &mut dummy;

That works the same way. It costs one allocation for a node that gets thrown away, which is tiny, but the stack version costs nothing. (In the stack version tail is a &mut ListNode, and assigning it a &mut Box<ListNode> works because Rust follows the box for you.)

There's also a one-line version of the two lines inside the loop:

tail = tail.next.insert(Box::new(ListNode::new(i * i)));

insert puts the box on the hook and hands back a changeable look at it. Same cost, less typing. It replaces whatever was on the hook, so only use it on an empty one.

Two lists in, one new list out

fn pairwise_sum(
    l1: Option<Box<ListNode>>,
    l2: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut a = l1;
    let mut b = l2;
    while a.is_some() || b.is_some() {
        let mut sum = 0;
        if let Some(node) = a {
            sum += node.val;
            a = node.next;
        }
        if let Some(node) = b {
            sum += node.val;
            b = node.next;
        }
        tail.next = Some(Box::new(ListNode::new(sum)));
        tail = tail.next.as_mut().unwrap();
    }
    dummy.next
}

That's the two-rows walk from section 3 with a tail bolted on. Each output node is brand new, built from numbers.

No peeking while the thumb is down

let mut tail = &mut dummy;
tail.next = Some(Box::new(ListNode::new(1)));
println!("{:?}", dummy.next); // looking while tail still holds the loan
tail = tail.next.as_mut().unwrap();

As long as tail will be used again, it is the only way into that row, and even printing dummy is a second way in. After the loop, when tail is finished, dummy is all yours again.

factEvery Box::new in a loop is one trip to the allocator. Building n new nodes costs n allocations. When the nodes you need already exist, you can skip all of that, which is the next section.

6

Moving real lockers

Section 5 rented new lockers and filled them with numbers. A lot of the time the lockers you need already exist. You want the same nodes, just in a different order, or fewer of them. Then you can leave the allocator alone completely and re-hang lockers you already own.

There's a catch, and it's a physical one. Hand someone a locker and you hand them everything inside it, including the key to the rest of the row. Hang node on your tail while node.next still holds the rest of the list, and the whole rest of the list comes along for the ride.

So before you hand a locker over, pocket its key:

cur = node.next.take();

take() lifts the key off the hook, gives it to you, and leaves the hook empty. Not a hole, an honest None. The node is now a clean single locker you can hang anywhere.

Here's a filter that keeps the even numbers, re-hanging the nodes it keeps:

fn keep_even(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut cur = head;
    while let Some(mut node) = cur {
        cur = node.next.take();
        if node.val % 2 == 0 {
            tail.next = Some(node);
            tail = tail.next.as_mut().unwrap();
        }
    }
    dummy.next
}

Odd nodes go out of scope at the end of their pass and are freed. Even nodes get re-hung. The dummy is on the stack, so the whole thing makes zero allocations.

Forget the take, and it doesn't compile

cur = node.next; // moved out, leaving a hole
if node.val % 2 == 0 {
    tail.next = Some(node); // handing over a node with a hole in it
    tail = tail.next.as_mut().unwrap();
}

In the reversal from section 4, a hole like this got filled on the very next line. Here it never gets filled, so Some(node) would be handing over a locker with a ripped-out hook. Rust won't let a partly moved value travel.

Several tails at once

Nothing says you get only one output row. Sort nodes into two piles as you go, then couple the piles at the end:

fn odds_then_evens(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut odd_dummy = ListNode::new(0);
    let mut even_dummy = ListNode::new(0);
    let mut odd_tail = &mut odd_dummy;
    let mut even_tail = &mut even_dummy;
    let mut cur = head;
    while let Some(mut node) = cur {
        cur = node.next.take();
        if node.val % 2 != 0 {
            odd_tail.next = Some(node);
            odd_tail = odd_tail.next.as_mut().unwrap();
        } else {
            even_tail.next = Some(node);
            even_tail = even_tail.next.as_mut().unwrap();
        }
    }
    odd_tail.next = even_dummy.next;
    odd_dummy.next
}

Two cardboard lockers, two thumbs. The last line, odd_tail.next = even_dummy.next;, works only because both thumbs are done by then. The loan that even_tail held on even_dummy ended the last time even_tail was used, so even_dummy is free to be emptied. Splitting into k piles is the same idea with k dummies.

Merging two sorted rows

Two sorted rows of lockers, one output row. Look at the front of each, take the smaller, repeat:

fn merge(
    l1: Option<Box<ListNode>>,
    l2: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut a = l1;
    let mut b = l2;
    while a.is_some() && b.is_some() {
        if a.as_ref().unwrap().val <= b.as_ref().unwrap().val {
            let mut node = a.unwrap();
            a = node.next.take();
            tail.next = Some(node);
        } else {
            let mut node = b.unwrap();
            b = node.next.take();
            tail.next = Some(node);
        }
        tail = tail.next.as_mut().unwrap();
    }
    if a.is_some() {
        tail.next = a;
    } else {
        tail.next = b;
    }
    dummy.next
}

One new tool: a.as_ref(). It turns "the hook" into "maybe a look at the locker on that hook", so a.as_ref().unwrap().val reads the front value without taking anything. Then a.unwrap(), with no as_ref, really does take the box out of a, and the next line puts the rest back.

The ending is worth a second look. When one row runs out, whatever is left of the other row hangs on in a single assignment, however long it is.

judgmentRe-hanging versus building new nodes is a trade. Re-hanging makes no allocations, but it uses up the input. Building new nodes from values costs one allocation per node, but if you only looked at the input, the input survives. When a function receives a list by value, whoever called it has already given it up, so re-hanging is usually the better deal.

7

Holding the hook

Rebuilding with a dummy and a tail is safe and clear, but it touches every node, including the ones you keep. Sometimes you'd rather stand in the row and fix one spot.

Think of the attendant at a coat check. The attendant never holds a coat. The attendant walks along the hooks. To remove a coat, they take it off its hook and hang up whatever that coat was carrying in its place. The hook is the thing they hold.

In C the classic deletion trick holds a pointer to a pointer: not the node, but the place where the node's address is stored. In Rust that's a changeable reference to a hook, &mut Option<Box<ListNode>>. Watch one walk a row and remove the negatives:

fn remove_negatives(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut hook = &mut head;
    while hook.is_some() {
        if hook.as_ref().unwrap().val < 0 {
            *hook = hook.as_mut().unwrap().next.take();
        } else {
            hook = &mut hook.as_mut().unwrap().next;
        }
    }
    head
}

Three things to see here.

*hook = ... writes onto the hook itself. The star means "the thing hook refers to", which is an actual hook in the row: head, or some node's next. Whatever used to hang there loses its last owner and is freed.

After a removal, hook stays put. A new locker just arrived on that hook and nobody has checked it yet. Only when a locker is kept does hook move on, to the hook inside that locker.

And there's no dummy. The variable head is a hook like any other, so removing the very first locker is the same line of code as removing one in the middle. (That's why the parameter is mut head: you can only lend out a changeable look at something you're allowed to change.)

The tempting version doesn't compile

while let Some(node) = hook {
    if node.val < 0 {
        *hook = node.next.take(); // refused
    } else {
        hook = &mut node.next;
    }
}

It looks like the same logic, and it is. Rust still says no.

modelnode is a loan taken out through hook. On the else branch, hook moves forward through that loan, so the checker treats the loan as possibly alive everywhere in the loop, including on the branch that overwrites *hook. It reasons about the loop as a whole and errs toward refusing. Check first with a short look that ends right away (hook.as_ref().unwrap().val), then act, and the conflict disappears.

Standing on a locker, fixing what follows

A second way to edit in place: hold a changeable look at one locker and repair what hangs after it.

fn drop_dips(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut cur = head.as_mut();
    while let Some(node) = cur {
        let v = node.val;
        while node.next.is_some() && node.next.as_ref().unwrap().val < v {
            node.next = node.next.take().unwrap().next;
        }
        cur = node.next.as_mut();
    }
    head
}

head.as_mut() gives "maybe a changeable look at the first locker." Inside the loop, v holds the value you're standing on, and the inner while keeps cutting out the next locker as long as it's smaller. Read node.next = node.next.take().unwrap().next; as: take the next locker off the hook, open it, keep the key it holds, hang that key on our hook. The opened locker has no owner after that line and is freed.

This shape can never remove the first locker, since you only ever fix what comes after the one you're standing on. Fine when the first node is always safe. If it isn't, use the hook version, or put a cardboard locker in front.

Inserting

Inserting is deleting run backwards. Walk the hook to the right spot, take what's hanging there, and hang a new locker that holds it:

fn insert_sorted(
    mut head: Option<Box<ListNode>>,
    val: i32,
) -> Option<Box<ListNode>> {
    let mut hook = &mut head;
    while hook.is_some() && hook.as_ref().unwrap().val < val {
        hook = &mut hook.as_mut().unwrap().next;
    }
    let rest = hook.take();
    *hook = Some(Box::new(ListNode { val, next: rest }));
    head
}

It handles every case, including an empty list and inserting before the first node, with no special code.

judgmentFor removals, the hook version and the rebuild version from section 6 both make zero allocations. The hook version leaves every kept node and its hook untouched. The rebuild version rewrites every kept node's next, which is a few extra memory writes and much easier to get right the first time. Pick the hook when you're changing a handful of spots in a long row. Pick the rebuild when the logic is fiddly.

8

Cut and couple

A train is a list. Uncouple between two cars and you have two trains. Couple two trains and you have one. Finding the right coupling means walking down the platform, but the uncoupling itself is one motion no matter how long the train is.

Cutting a list after k nodes: walk a hook k steps, then take() whatever hangs there.

fn split_after(
    head: &mut Option<Box<ListNode>>,
    k: usize,
) -> Option<Box<ListNode>> {
    let mut hook = head;
    let mut i = 0;
    while i < k && hook.is_some() {
        hook = &mut hook.as_mut().unwrap().next;
        i += 1;
    }
    hook.take()
}

This function takes &mut Option<Box<ListNode>>, a changeable look at a hook. It edits your list where it sits (the front part stays in your variable) and hands you the piece it cut off. If the list is shorter than k, nothing gets cut and you get back None.

Coupling is the reverse: walk to the empty hook at the end of the first row and hang the second row there.

fn join(
    mut a: Option<Box<ListNode>>,
    b: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut hook = &mut a;
    while hook.is_some() {
        hook = &mut hook.as_mut().unwrap().next;
    }
    *hook = b;
    a
}

factCutting or coupling moves exactly one 8-byte key, whether there are three lockers behind it or three million. Finding the spot is what costs: a walk of k steps to cut, a walk to the end to couple.

Gluing moves together

Most rearranging comes down to cut, do something to a piece, couple. Moving the first k nodes to the back:

fn rotate_left(head: Option<Box<ListNode>>, k: usize) -> Option<Box<ListNode>> {
    let mut front = head;
    let back = split_after(&mut front, k);
    join(back, front)
}

Chopping a list into pieces of size k, kept in a Vec. A Vec<Option<Box<ListNode>>> is a row of hooks, 8 bytes each; the lockers themselves don't move.

fn chunks(head: Option<Box<ListNode>>, k: usize) -> Vec<Option<Box<ListNode>>> {
    let mut parts = Vec::new();
    let mut rest = head;
    while rest.is_some() {
        let after = split_after(&mut rest, k);
        parts.push(rest);
        rest = after;
    }
    parts
}

Reversing just a middle stretch, positions from up to (not including) to, counting from 0. This one uses reverse from section 4:

fn reverse_middle(
    head: Option<Box<ListNode>>,
    from: usize,
    to: usize,
) -> Option<Box<ListNode>> {
    let mut front = head;
    let mut middle = split_after(&mut front, from);
    let back = split_after(&mut middle, to - from);
    join(join(front, reverse(middle)), back)
}

And interleaving two rows, one locker from each in turn, until both are empty:

fn weave(
    l1: Option<Box<ListNode>>,
    l2: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut a = l1;
    let mut b = l2;
    while a.is_some() || b.is_some() {
        if let Some(mut node) = a {
            a = node.next.take();
            tail.next = Some(node);
            tail = tail.next.as_mut().unwrap();
        }
        if let Some(mut node) = b {
            b = node.next.take();
            tail.next = Some(node);
            tail = tail.next.as_mut().unwrap();
        }
    }
    dummy.next
}

judgmentWhen the cut position depends on the length (the middle, the last k, n equal parts), count first with length from section 2, then cut. Two walks, no extra memory, and the code reads like the plan. That's usually a better deal than trying to find the spot in one clever walk.

9

Two fingers

A lot of list techniques walk two pointers through the same row. One moves one step at a time and another moves two. Or one runs k steps ahead of the other. In Rust, two lookers are no problem at all. Finding the middle value, for instance:

fn middle_value(head: &Option<Box<ListNode>>) -> i32 {
    let mut slow = head;
    let mut fast = head;
    while fast.is_some() && fast.as_ref().unwrap().next.is_some() {
        slow = &slow.as_ref().unwrap().next;
        fast = &fast.as_ref().unwrap().next.as_ref().unwrap().next;
    }
    slow.as_ref().unwrap().val
}

fast moves two hooks per pass, slow moves one. When fast runs out of row, slow is halfway. The while condition checks both hooks fast is about to jump over, so it never unwraps an empty one. (With an even number of nodes this lands on the second of the two middle nodes.)

The trouble starts when one finger needs to change things. Think of the row as a museum exhibit. A crowd of sightseers can wander it at once. The mover, the one person allowed to rearrange lockers, works alone: while anyone is looking, the mover waits, and while the mover works, nobody looks.

A looker and a changer in the same row doesn't compile

let mut ahead = &dummy.next; // a looking finger
let mut i = 0;
while i < k {
    ahead = &ahead.as_ref().unwrap().next;
    i += 1;
}
let mut behind = &mut dummy; // a changing finger, same list: refused
while let Some(node) = ahead {
    ahead = &node.next;
    behind = behind.next.as_mut().unwrap();
}

ahead is still looking when behind asks for a changeable loan of the same row. In C this is the textbook way to remove the k-th node from the end. In Rust it needs a different plan.

There are four ways out. Each has a price.

Exit 1: count first

Turn "k-th from the end" into "position n minus k from the front", then walk one changeable hook there.

fn remove_at(
    mut head: Option<Box<ListNode>>,
    index: usize,
) -> Option<Box<ListNode>> {
    let mut hook = &mut head;
    let mut i = 0;
    while i < index && hook.is_some() {
        hook = &mut hook.as_mut().unwrap().next;
        i += 1;
    }
    if hook.is_some() {
        *hook = hook.as_mut().unwrap().next.take();
    }
    head
}
let n = length(&head);
remove_at(head, n - k)

Two walks instead of one, nothing extra in memory. This is the default choice, and most two-finger tricks translate into it: the middle is position n / 2, the last k start at n minus k, and so on.

Exit 2: copy to a clipboard

Write the numbers on a clipboard (the to_vec from section 2), do anything you like with them, and if needed write them back into the same nodes:

fn write_back(head: &mut Option<Box<ListNode>>, values: &Vec<i32>) {
    let mut cur = head.as_mut();
    let mut i = 0;
    while let Some(node) = cur {
        node.val = values[i];
        i += 1;
        cur = node.next.as_mut();
    }
}
fn sort_values(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut values = to_vec(&head);
    values.sort();
    write_back(&mut head, &values);
    head
}

head.as_mut() and node.next.as_mut() walk the row with a changeable look, so node.val = ... overwrites numbers in place. No node moves. That's also the catch: this changes values, not nodes. If a task says the nodes themselves must be rearranged, writing values back doesn't count.

Exit 3: make a copy of the row

Sometimes you want to return a list that starts in the middle. You can't hand out the middle of a row and keep the front: the middle locker's key lives inside the locker before it. With two lookers you could find the middle and then copy everything from there on:

slow.clone() // a fresh copy of every node from slow onward

Or give up the front half on purpose, which is often what the task wants anyway:

fn from_middle(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let n = length(&head);
    let mut cur = head;
    let mut i = 0;
    while i < n / 2 {
        cur = cur.unwrap().next; // the front node is freed right here
        i += 1;
    }
    cur
}

cur.unwrap().next takes the box, pulls out its key, and the emptied locker is freed right on that line.

factOn a 1000-node list, counted with an allocation counter: the clone() route made 500 new allocations (a fresh copy of every node from the middle on). The move route made none, and freed the 500 front nodes along the way.

Exit 4: step outside the rules

Raw pointers let two fingers do whatever they like, with nobody checking. That's section 14.

Why the clipboard is often the fast choice

Copying into a Vec costs memory, so it's tempting to think it's the slow option. The machine disagrees.

factThose numbers were measured. The Vec takes about a quarter of a nanosecond per number. A list whose nodes happened to be allocated one after another takes about 4. The same list with its nodes linked in a shuffled order takes about 183, roughly 750 times the Vec.

modelA Vec is one block of memory read front to back, and the processor fetches the next chunk before you ask for it. A list is a trail of addresses: you can't know where node 5 lives until you've read node 4. When the nodes sit close together the trail is a series of short hops. When they're scattered, nearly every hop is a full trip out to main memory, and the processor just waits.

judgmentCopying to a Vec and working there is often faster in practice than clever pointer work on the list, even counting the copy. Memory is what you pay. When a task caps extra memory, you pay in time instead.

Recursion

Picture a hallway with one person standing at each locker. You ask the first person how long the row is. They can't answer yet, so they ask the person at the next locker, who asks the next one, and so on. The last person sees an empty hook and says "zero." Then the answers travel back: one, two, three, all the way to you.

fn length_rec(head: &Option<Box<ListNode>>) -> usize {
    match head {
        None => 0,
        Some(node) => 1 + length_rec(&node.next),
    }
}

match is if let for every case at once: you list each shape the value can have, and what to do for each. A list is either empty (None) or a box with a rest behind it (Some(node)). Rust checks that you covered every case, so you can't forget the empty list.

Each person waiting in the hallway is a stack frame: a small block of memory holding that call's variables while it waits for the call after it. Keep that picture. It comes back in a minute.

Merging, the short way

fn merge(
    l1: Option<Box<ListNode>>,
    l2: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    match (l1, l2) {
        (None, rest) | (rest, None) => rest,
        (Some(mut a), Some(mut b)) => {
            if a.val <= b.val {
                a.next = merge(a.next, Some(b));
                Some(a)
            } else {
                b.next = merge(Some(a), b.next);
                Some(b)
            }
        }
    }
}

Two new pieces of pattern syntax. (l1, l2) packs both lists into a pair so you can match on both at once. And (None, rest) | (rest, None) => rest is two patterns joined by |, meaning either one: if one list is empty, the answer is the other list, whatever it holds.

The last arm does the real work. Both lists have a front locker. The smaller front wins. Its next becomes the merge of everything that's left, and the winner goes back as the head. a.next is moved out to be passed down, and the same line fills the hole with the answer, so nothing is ever left half-moved.

Compare it with the loop in section 6. Same job, same result, no dummy and no tail, and it reads almost like the definition of merging.

Divide and conquer

With cutting and merging in hand, sorting a list is three moves: cut it in half, sort each half, merge the halves.

fn sort(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let n = length(&head);
    if n < 2 {
        return head;
    }
    let mut front = head;
    let back = split_after(&mut front, n / 2);
    merge(sort(front), sort(back))
}

length and split_after are the ones from sections 2 and 8.

The hallway has a length

factRecursive merge goes as deep as the two lists are long, combined. On an 8 MiB stack it ran out of room at about 50 thousand nodes in a debug build, and around 260 thousand in an optimized build (the frames are smaller there). The loop version from section 6 has no depth at all. Sorting's own depth is small, about log2 n levels of cutting in half; it's the merges inside it that go deep.

judgmentRecursion earns its place when the lists are short, or when the depth grows like log n instead of n. For long rows, the loop is the safe choice. When the recursive version is easier to think about, write it first, get it right, and convert it to a loop if the input size calls for it.

11

Lists inside other things

A list is just a value. You can keep one inside a struct, line several up in a Vec, or pull its nodes apart and drop them into other containers. None of that moves a locker. Containers hold keys.

Think of a post office sorting room with different counters. One counter keeps a single row and answers questions about it. One lets you take parcels off either end of a conveyor. One keeps a stamp book of everything it has seen. One always hands you the lightest parcel in the room. Each has its own rules.

A struct that keeps a list

A struct groups named fields into a new type, the way ListNode groups val and next. An impl block attaches functions to that type. A function in an impl whose first parameter is &self or &mut self is a method: it runs on one particular value and you call it with a dot.

Start with a tiny random number generator, so picking a random node needs no library at all:

struct Rng {
    state: u64,
}

impl Rng {
    fn next(&mut self) -> u64 {
        let mut x = self.state;
        x ^= x << 13;
        x ^= x >> 7;
        x ^= x << 17;
        self.state = x;
        x
    }
}

The generator remembers one number, state. Each call scrambles it with three shifts and three exclusive-ors (^), stores the result, and returns it. The numbers follow a long fixed sequence that looks random enough to pick a position. It is not fit for anything secret. The method takes &mut self because it changes state.

Now a struct that keeps a list and picks a random value from it:

struct Picker {
    head: Option<Box<ListNode>>,
    rng: Rng,
}

impl Picker {
    fn new(head: Option<Box<ListNode>>) -> Self {
        Picker {
            head,
            rng: Rng {
                state: 88172645463325252,
            },
        }
    }

    fn pick(&mut self) -> i32 {
        let n = length(&self.head) as u64;
        let mut steps = self.rng.next() % n;
        let mut cur = &self.head;
        while let Some(node) = cur {
            if steps == 0 {
                return node.val;
            }
            steps -= 1;
            cur = &node.next;
        }
        0 // only reached if the list is empty
    }
}

fn new(...) -> Self is the usual name for a function that builds a value; Self means "this type", here Picker. pick counts the nodes, rolls a number from 0 to n minus 1 with % n (the remainder after dividing by n), and walks that many steps.

Two walks per pick. Here's a way to do it in one, without knowing the length in advance:

impl Picker {
    fn pick_one_pass(&mut self) -> i32 {
        let mut chosen = 0;
        let mut seen: u64 = 0;
        let mut cur = &self.head;
        while let Some(node) = cur {
            seen += 1;
            if self.rng.next() % seen == 0 {
                chosen = node.val; // node number `seen` wins with chance 1/seen
            }
            cur = &node.next;
        }
        chosen
    }
}

Walk once and keep a current choice. Node number k replaces the choice with chance 1 in k. Check it on three nodes. Node 3 is chosen with chance 1/3. Node 2 gets picked at its turn with chance 1/2 and survives node 3 with chance 2/3, so 1/2 × 2/3 = 1/3. Node 1 is picked for sure, then survives both: 1/2 × 2/3 = 1/3. Fair all round.

fact30,000 picks from a list of 1, 2, 3 with each method: pick chose them 10,019, 9,930 and 10,051 times; pick_one_pass chose them 10,025, 10,021 and 9,954 times.

Why the generator lives in its own struct

let mut cur = &self.head; // borrows part of self
while let Some(node) = cur {
    seen += 1;
    if self.next_random() % seen == 0 {
        // a method borrows ALL of self
        chosen = node.val;
    }
    cur = &node.next;
}

With the generator as a method on Picker itself, the call needs a changeable loan of all of self, while cur is still looking at self.head. Putting the generator in its own field, self.rng, lets Rust see that the loan on self.rng and the look at self.head touch different fields, and both are allowed.

judgmentThree ways to pick, three prices. Count-and-walk: two walks per pick, no memory. One pass: one walk per pick, no memory. Copy the values into a Vec once inside new: memory for every value, then each pick is a single index. If you'll pick many times from a list that never changes, the Vec wins by a mile.

Taking from both ends

The next containers come from the standard library. A use line at the top of the file brings their names into scope:

use std::cmp::Ordering;
use std::collections::{BinaryHeap, HashSet, VecDeque};

A VecDeque is a conveyor you can load and unload at either end. Detach every node (with take, as always) and load them on:

fn detach_all(head: Option<Box<ListNode>>) -> VecDeque<Box<ListNode>> {
    let mut nodes = VecDeque::new();
    let mut cur = head;
    while let Some(mut node) = cur {
        cur = node.next.take();
        nodes.push_back(node);
    }
    nodes
}

Each element is a Box<ListNode>, one 8-byte key per locker. pop_front() and pop_back() hand you a node from either end, ready to hang on a tail in whatever order the task asks for: front, back, front, back, or anything else. Memory cost: one key per node.

Remembering what you've seen

fn remove_repeats(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut seen = HashSet::new();
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    let mut cur = head;
    while let Some(mut node) = cur {
        cur = node.next.take();
        if seen.insert(node.val) {
            tail.next = Some(node);
            tail = tail.next.as_mut().unwrap();
        }
    }
    dummy.next
}

seen.insert(v) adds v to the set and returns true if it wasn't there before, so the first copy of each value is kept and later copies are freed. A HashMap does the same job with something attached to each value: a count, a position, a running total. It's the tool whenever a task asks "have I been here before, and what did I know then?"

Always the smallest next

A BinaryHeap is the counter that always hands over the biggest item in the room. To merge many sorted lists you want the smallest instead. That means teaching ListNode to compare backwards.

This is where traits come in. A trait is a promise that a type knows how to do something. A heap only accepts items that promise they can be ordered, the Ord trait. ListNode doesn't make that promise, so you write it:

impl Ord for ListNode {
    fn cmp(&self, other: &Self) -> Ordering {
        other.val.cmp(&self.val) // flipped: smaller val counts as "greater"
    }
}

impl PartialOrd for ListNode {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

cmp returns an Ordering: less, equal or greater. Comparing other.val to self.val, instead of the other way round, flips the order, so the heap's "biggest" is the node with the smallest value. PartialOrd is a second, looser promise that Ord requires; the body just reuses cmp. Rust lets you write these because ListNode is defined in your own code. You can't add a standard trait to a type that belongs to someone else's library.

fn merge_many(lists: Vec<Option<Box<ListNode>>>) -> Option<Box<ListNode>> {
    let mut heap = BinaryHeap::new();
    for list in lists {
        if let Some(node) = list {
            heap.push(node);
        }
    }
    let mut dummy = ListNode::new(0);
    let mut tail = &mut dummy;
    while let Some(mut node) = heap.pop() {
        if let Some(next) = node.next.take() {
            heap.push(next);
        }
        tail.next = Some(node);
        tail = tail.next.as_mut().unwrap();
    }
    dummy.next
}

Load each list's front node. Then: take the smallest, put its successor in its place, hang the smallest on the tail. The heap only ever holds one node per list.

judgmentThere's a quiet inconsistency in that Ord. Two nodes with the same val compare as equal under it, while the derived == compares the whole lists behind them and might say they differ. The heap never notices. If you'd rather not write a trait at all, merge in pairs instead, round after round, with the merge from section 6 or 10:

fn merge_many_pairwise(
    mut lists: Vec<Option<Box<ListNode>>>,
) -> Option<Box<ListNode>> {
    if lists.is_empty() {
        return None;
    }
    while lists.len() > 1 {
        let mut next_round = Vec::new();
        while lists.len() >= 2 {
            let a = lists.pop().unwrap();
            let b = lists.pop().unwrap();
            next_round.push(merge(a, b));
        }
        if lists.len() == 1 {
            next_round.push(lists.pop().unwrap());
        }
        lists = next_round;
    }
    lists.pop().unwrap()
}

Each round halves the number of lists. With k lists holding N nodes between them, both approaches do work proportional to N × log k. The heap version needs the trait; the pairwise version needs nothing new.

Costs you didn't write

Back to the line above ListNode: #[derive(PartialEq, Eq, Clone, Debug)]. It asks the compiler to write some code for you. That's handy. Read the fine print anyway, because every one of those generated functions walks the entire list.

let a = Some(Box::new(ListNode {
    val: 1,
    next: Some(Box::new(ListNode::new(2))),
}));
let b = a.clone(); // every node copied: 2 new allocations
println!("{}", a == b); // true, after comparing node by node
println!("{:?}", a);

Running it prints:

true
Some(ListNode { val: 1, next: Some(ListNode { val: 2, next: None }) })
  • Clone copies every node. factCloning a 1000-node list made 1000 allocations.
  • PartialEq and Eq give you ==, which compares node by node down both lists. No allocations, but a full walk.
  • Debug lets {:?} print the list, nested as you see above (boxes don't show up in the output). Great for checking your work, painful for long lists.

The rest of the definition is quieter. pub makes a field visible outside the module it's defined in. #[inline] is a hint to the optimizer. Neither changes anything you write.

Handing the row back

One more piece of code you never wrote: the cleanup when a list goes away. It sounds simple. But the desk can't sign off on locker 1 until locker 2 has come back, and locker 2 is waiting on locker 3. Freeing a list is the hallway from section 10 again: one stack frame per node, all waiting.

factDropping a list the default way overflowed an 8 MiB stack at about 130 thousand nodes in a debug build, and about 260 thousand in an optimized build.

The fix is to free it in a loop, taking each node's key out before the node goes:

let mut cur = head;
while let Some(mut node) = cur {
    cur = node.next.take(); // node goes with an empty hook: a one-step free
}

factThis freed a 3-million-node list without trouble, in both debug and optimized builds.

judgmentWith a few thousand nodes you will never notice any of this. It matters for long lists: big test inputs, lists kept around in a long-running program, or anything built in a loop that never stops growing.

When a list meets a tree

Some tasks connect a list with a binary tree. You might build a tree from a list's values, or check whether a list's values appear as a path down a tree. The tree node you'll be given looks like this:

use std::cell::RefCell;
use std::rc::Rc;
#[derive(Debug, PartialEq, Eq)]
pub struct TreeNode {
    pub val: i32,
    pub left: Option<Rc<RefCell<TreeNode>>>,
    pub right: Option<Rc<RefCell<TreeNode>>>,
}

Two new wrappers, Rc and RefCell. Their real story is the next topic, so here's the one-line version of each. Rc is a key that can be copied: a locker with several owners, freed when the last one lets go. RefCell moves the "many lookers or one changer" check from compile time to while the program runs.

For now, two recipes are enough.

Building. Wrap three times: the node in RefCell, that in Rc, that in Some.

fn tree(
    val: i32,
    left: Option<Rc<RefCell<TreeNode>>>,
    right: Option<Rc<RefCell<TreeNode>>>,
) -> Option<Rc<RefCell<TreeNode>>> {
    Some(Rc::new(RefCell::new(TreeNode { val, left, right })))
}

Reading. Call .borrow() to open a node for looking. After that, t.val and &t.left work just like looking at a ListNode.

fn tree_sum(root: &Option<Rc<RefCell<TreeNode>>>) -> i32 {
    match root {
        None => 0,
        Some(node) => {
            let t = node.borrow();
            t.val + tree_sum(&t.left) + tree_sum(&t.right)
        }
    }
}
let root = tree(2, tree(1, None, None), tree(3, None, None));
println!("{}", tree_sum(&root)); // 6

Two list tricks carry straight over. Copying a list's values into a Vec (section 2) gives you the random access that tree building usually wants, like grabbing the middle value for the root and then the middle of each half. And when a list has to be matched against a tree, walk the list with a look (&node.next) and the tree with .borrow(), step by step, side by side.

Past one owner

Everything so far obeys the one-key rule. Some shapes can't be built under it at all:

  • a row whose last locker holds the key to one in the middle (a cycle),
  • two rows that share the same tail,
  • lockers that also hold the key to the one before (a doubly linked list),
  • a key to one locker in the middle of a row, handed to you without the rest of the row.

Every one of them needs a locker with two keys. Box can't say that. It's not a missing feature, it's the rule doing its job.

There is a way around the rule, and it's the equivalent of picking the lock:

let node: &ListNode = list.as_ref().unwrap();
let p: *const ListNode = node; // an address with no rules attached
let v = unsafe { (*p).val }; // you promise p still points at a live node

*const ListNode is a raw pointer, an address with no rules attached. Copy it, keep it, have ten of them pointing at the same node. Reading through one needs an unsafe block, which is you telling the compiler: I've checked this myself. If the node has been freed or moved by the time you read, the program reads garbage or crashes, and nothing warns you first.

judgmentReal Rust code does use raw pointers, inside small, carefully reviewed building blocks. For list work like everything on this page, there's always a safe route through sections 1 to 13, and it's the one to take.

The safe way to give a locker several owners is Rc, the copyable key from section 13, together with RefCell for changing what's inside. That's where graphs live, and it's where this goes next.
